─── JUSTIFICATION TEXT (for coding) ───

[DOMAIN]
Value: ICS
Evidence: Abstract: Focuses on "Programmable logic controllers (PLCs)," which are "essential components of Industrial Control System (ICS)". The case study involves "traffic light applications"

[INTERACTION LEVEL]
Value: High
Evidence: Section 1 / 4.1.1: PLCHoney is designed for "engaged interaction" by funneling aggressive activity (like writing coils and registers) to a "consolidated OpenPLC and process simulation",. It is explicitly framed as an improvement over existing high-interaction models like HoneyPLC

[THREAT MODEL]
Value: ICS attackers targeting PLCs
Evidence: Section 1/3.1/Page 2: Targets attackers who exploit PLCs to "gather attacker information and attack tactics"
. It specifically monitors those performing "Device Enumeration," "overwriting or injection attacks," and "data injection"

[IRB / ETHICS COMMITTEE]
Value: No
Evidence: A review of the entire paper confirms no mention of an "Institutional Review Board," "ethics committee," or human subject protocols

[CONSENT MODEL]
Value: Implicit
Evidence: Section 3.1 / Page 2: The system is designed to "deceive attackers into believing a real PLC... is behind".
It was exposed to the Internet to "attract internet requests," assuming interaction is attacker-initiated without disclosure

[DATA TYPES COLLECTED]
Value: IPs, command interactions, and I/O status
Evidence: Section 3.4 / Abstract: The engine applies analysis to "identify the source IP information of the attackers"
. It records "requests for memory layout discovery," "PLC I/O status," and "interaction logs"

[PROTOCOLS & PORTS]
Value: Modbus/TCP (502) - implemented and tested; S7comm and DNP3 listed only as future/planned protocol support
Evidence: Section 3.1: "we plan to simulate a rich set of functionalities for widely used PLC-related protocols, such as Modbus, TCP/IP, S7comm, DNP3, etc." (future intent). Section 4.1.1/4.1.2 confirms only Modbus/TCP port 502 was actually implemented and received real traffic: "We were able to receive 52 requests for TCP port connections on port 502."

[DATA SENSITIVITY]
Value: High
Evidence: Section 3.4: "requests for memory layout discovery," "input/output data of the PLC," and "reading and writing coils and registers". 
It monitors the "dynamic behavior of the physical process simulator," which represents physical-world effects.

[DATA MINIMIZATION]
Value: Yes (Partial)
Evidence: Figure 2 caption: "(The IP address is blocked for privacy)"; Figure 3 caption: same note. No minimization is applied to the actual collected/stored data - only to what's shown in the published paper.

[DATA RETENTION POLICY]
Value: Not discussed
Evidence: Section 4.2.1: Mentions that a "logger" records behavior in JSON and TSV formats for offline analysis, but provides no timeline for deletion or storage expiration

[DATA SHARING]
Value: Source code publicly released on GitHub
Evidence: Section 4: "The source code of the implementation is open source and results are publicly available" with footnote: "Project link: https://github.com/sys-ris3/PLCHoney"

[JURISDICTION / LEGAL]
Value: Not discussed
Evidence: Section 4.1.2: Deployed the system on the internet to attract "52 requests for TCP port connections," but provides no analysis of legal jurisdiction, GDPR, or data protection compliance

[CONTAINMENT & HARM]
Value: Virtualization and Docker isolation
Evidence: Section 3.2: Uses "“soft PLCs” in Docker containers" to prevent "irreversible firmware and memory corruption". 
Virtualization is used to ensure no real physical process manipulation occurs

[DECEPTION FRAMING]
Value: Purely technical
Evidence: Section 3.1: Deception is framed as a technical goal to "deceive attackers into believing a real PLC from a specific brand is behind" and to provide Page 2: "better interactions" through simulated plant behavior

[RESEARCHER RESPONSIBILITY]
Value: Implicit
Evidence: Section 1: Defensive intent is framed as "identifying and moderating potential attacks". 
Researcher responsibility is achieved via "safety via virtualization" to avoid disrupting real infrastructure

[ETHICAL GAPS]
Value: Structural Ethical Vacuum
Evidence: Represents the "ethics-by-containment" model. There is no explicit ethical discussion; instead, ethics are "assumed through virtual design" and technical isolation

The paper also demonstrates active fingerprinting of a real third-party organization: an attacker's Modbus transaction ID (hex 1337, "leet") was traced via Whois to a named commercial security company (Section 4.1.2, footnote 2), though the paper does not name the company or discuss the ethics of identifying real third-party scanning infrastructure.

[RELEVANCE TO PROJECT]
Value: Containment as ethical safeguard.
Evidence: Section 3.3: Serves as a primary example of ethics-by-containment. 
It creates a high-fidelity Digital Twin using a "Physical Process Simulator" to record the "dynamic behavior" of traffic light timing sequences without disrupting real infrastructure.
Unlike HoneySat, it lacks formal IRB oversight, confirming that technical safety via virtualization is used as a total substitute for normative reasoning.

[DEPLOYMENT]
Value: Yes (Internet-facing Proxy)
Evidence: Section 4.1.2: "Our proxy was set up on the internet and run for 2 days" to attract and handle Modbus requests
